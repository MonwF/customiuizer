# CustoMIUIzer 性能、稳定性与兼容性方法论

## 一、核心原则

宏观上，真正决定性能、内存和耗电的，不是代码行数、函数层级或语法是否简短，而是模块让系统额外执行了多少工作。

模块的额外成本可以概括为：

> 额外成本 ≈ 触发频率 × 单次成本 × 进程数量 × 存活时间

因此，本项目的核心工程原则是：

> 功能关闭时接近零额外成本；功能开启时只响应真实事件；高频路径无不必要分配、无重复反射、无阻塞；兼容代码限制在明确边界内。

优先级固定为：

1. 实际可运行；
2. 功能行为正确；
3. 系统与进程稳定；
4. API、ROM 和版本兼容；
5. 性能、内存和功耗；
6. 可维护性；
7. 代码简洁度和形式统一。

任何性能优化都不能以功能静默失效、异常被吞掉、兼容性下降或代码不可维护为代价。

---

## 二、宏观优化优先级

| 方向           |  潜在收益 | 核心做法                                   |
| ------------ | ----: | -------------------------------------- |
| 减少无效 Hook    |    很高 | 未启用功能不注册 Hook，不在高频回调中反复判断开关            |
| 缩小进程作用域      |    很高 | 每个包和进程只加载真正需要的功能                       |
| 消灭轮询和空唤醒     |    很高 | 优先使用系统事件、监听器和生命周期回调                    |
| 生命周期与资源所有权   |    很高 | Hook、Receiver、Observer、线程和缓存必须有明确所有者   |
| 避免重复初始化      |     高 | 防止同一进程重复注册 Hook、监听器和调度任务               |
| 控制长期内存       |     高 | 缓存有上限，不长期持有 Context、View、ClassLoader   |
| 统一有限调度资源     |    中高 | 复用主线程 Handler 和有界后台执行器，但避免中央组件膨胀       |
| 优化绘制与动画路径    |    中高 | 高频绘制中复用对象，不重复创建 Drawable、Shader、Matrix |
| 优化 Hook 参数访问 |     中 | 不读取参数时不复制，只读取单个参数时避免完整数组转换             |
| 反射与资源查找缓存    | 视频率而定 | 只缓存真正重复、稳定且可安全复用的结果                    |
| 删除普通方法层级     |    很低 | ART/R8 通常能够内联，不应作为主要优化方向               |

优化优先处理“调用次数多、进程范围广、生命周期长”的问题，而不是优先处理几十纳秒级的普通函数调用。

---

## 三、功能关闭时接近零成本

这是 Xposed/LSPosed 模块最重要的性能原则。

如果功能关闭后仍然注册 Hook，那么目标方法每次执行时，仍然需要经过框架分发、模块回调和偏好判断。单次成本可能很小，但 SystemUI、Launcher 和 system_server 中的高频方法会将成本持续放大。

理想状态：

* 不注册对应 Hook；
* 不加载相关类和资源；
* 不初始化 DexKit、反射成员或大型缓存；
* 不注册 Receiver、Observer、Listener 和 Callback；
* 不创建线程、协程或延迟任务；
* 不进行周期刷新；
* 不打印该功能的运行日志。

对于必须在进程启动阶段决定是否安装的功能，设置开启后可以要求重启对应进程或设备生效。

这种行为应在设置界面明确提示，避免为了“即时生效”而让所有关闭功能长期保持运行成本。

动态关闭已经安装的 Hook 时，应根据实际成本选择：

* 能安全 `unhook` 的，立即注销；
* 不能可靠注销的，保留轻量状态判断并提示重启；
* 不要为了动态切换建立复杂且不稳定的全局管理系统。

---

## 四、按进程建立启动清单

Xposed 模块进入多个进程后，静态字段、缓存、线程和对象会在每个进程中分别存在。

因此必须建立明确的“功能—进程”关系：

* `system_server`：系统服务、权限、窗口、电源、锁屏安全等 Hook；
* `com.android.systemui`：状态栏、控制中心、通知、锁屏及 SystemUI 绘制；
* `com.miui.home`：桌面、文件夹、手势和最近任务；
* 模块设置进程：设置界面、偏好写入和服务连接；
* 其他应用：只有存在明确功能需求时才初始化对应代码。

在确定目标包和进程之前，不应提前初始化：

* Remote Preferences；
* ResourceHooks；
* DexKit；
* 图像或 Drawable 缓存；
* 大型反射缓存；
* 后台线程池；
* 与当前进程无关的功能类。

入口层应尽早完成包名、进程名、Android 版本和框架能力判断，然后立即退出无关路径。

## 五、事件驱动优先，避免轮询

省电收益最大的优化通常不是减少一次函数调用，而是避免一次线程调度、进程唤醒或 Binder 查询。

刷新机制优先级：

1. 系统原生 Callback 或事件；
2. BroadcastReceiver；
3. ContentObserver 或 SharedPreferences Listener；
4. 与 Activity、Fragment、View 生命周期绑定的刷新；
5. 复用系统已有刷新节奏；
6. 最后才考虑周期任务。

必须使用周期任务时：

* 功能关闭后立即停止；
* 页面不可见后停止；
* 进程或对象销毁时取消；
* 多项任务尽量共享有限调度资源；
* 防止重复注册产生多个相同循环；
* 不允许永久执行“查询后无变化，再安排下一次”的空循环；
* 周期应根据真实业务需求确定，而不是为了界面看起来实时而盲目提高频率；
* 优先跟随系统现有刷新节奏，不人为制造额外唤醒。

不要机械地将所有任务对齐整秒。是否对齐应根据系统原有调度方式、刷新来源和实际测量决定。

## 六、资源所有权必须明确

每个长期资源都必须回答四个问题：

1. 谁创建？
2. 谁持有？
3. 谁停止或注销？
4. 进程重建或页面销毁后是否会重复创建？

需要治理的对象包括：

* HookHandle；
* Receiver；
* ContentObserver；
* Preference Listener；
* View Callback；
* Handler Runnable；
* CoroutineScope；
* Executor；
* Timer；
* Animator；
* DexKit 实例；
* Bitmap、Drawable 和图像缓存；
* Context、View 和 ClassLoader 引用。

基本规则：

* 注册操作必须幂等；
* 注销操作允许重复调用；
* Activity/Fragment 资源绑定对应生命周期；
* 进程级资源由明确的进程级所有者管理；
* 不让静态字段持有 Activity、Fragment、View 或临时 Context；
* 不让后台任务捕获已销毁的界面对象；
* 缓存必须有容量、生命周期或淘汰策略。

可以建立有限的进程级运行时组件，统一持有偏好快照、主线程 Handler、后台执行器和日志限流状态。

但它不能演变成包含所有功能、所有状态和所有生命周期的全局“上帝对象”。

## 七、热路径和冷路径分离

### 热路径

包括：

* `onDraw()`；
* 动画帧；
* 状态栏刷新；
* 控制中心刷新；
* 网络速度更新；
* 触摸、滑动和手势；
* 通知绑定；
* 图标加载；
* 音频频谱回调；
* SystemUI 高频方法 Hook；
* Launcher 高频布局和滚动回调。

热路径要求：

* 不执行反射查找；
* 不查询 DexKit；
* 不读取磁盘；
* 不同步调用远程 Binder；
* 不创建临时数组、集合、Pair、Triple 或大量 lambda；
* 不使用复杂集合链式操作；
* 不重复格式化字符串；
* 不打印正常运行日志；
* 不持有大范围锁；
* 不重复读取 SharedPreferences；
* 尽量只读取已准备好的不可变状态或简单原子状态。

### 冷路径

包括：

* 模块启动；
* 首次 Hook 安装；
* 设置变化；
* 页面创建；
* 首次资源解析；
* ROM 兼容性探测。

反射查找、资源解析、DexKit 搜索和对象构建应尽量集中在冷路径中，将结果准备好供热路径直接使用。

不要为了避免所有对象创建而把冷路径代码写得异常复杂。优化重点是避免高频重复成本，而不是禁止所有分配。

## 八、Hook 参数与调用链优化

Hook 适配层应保持明确、稳定和低成本。

原则：

* 回调未读取参数时，不主动复制参数；
* 只读取单个参数时，优先使用单参数访问能力；
* 只有修改参数时才构建新的参数数组；
* 保留 Hook priority、before/after 顺序和异常传播语义；
* 提前返回、替换结果和抛出异常必须与原行为一致；
* 不在每次回调中重复检查 after 方法是否存在；
* 不在高频 Hook 中动态查找 Method、Field 或 Class；
* 不为少量低频 Hook 建立复杂的通用缓存体系。

兼容层的价值是稳定隔离框架差异，而不是隐藏所有业务逻辑。

---

## 九、API 101 / API 102 兼容边界

项目后续应采用单 APK 同时兼容 libxposed API 101 和 API 102。

基本原则：

* 使用 API 102 编译；
* `minApiVersion=101`；
* `targetApiVersion=102`；
* API 101 作为最低运行基线；
* 公共 Hook 路径只依赖 API 101 已有能力；
* API 102 专属能力集中在独立边界中；
* 在冷路径或初始化入口判断实际 `getApiVersion()`；
* 不在高频 Hook 回调中反复判断 API 版本；
* API 101 路径不得加载或解析 API 102 专属类型；
* 不通过反射访问 libxposed API 来绕过限制；
* 不混用 `de.robv.android.xposed` Legacy API。

API 102 的 Hot Reload、Hook 原子替换和 detach 生命周期属于独立能力。

在没有完成线程、Receiver、Observer、JNI、HookHandle 和 ClassLoader 所有权治理前，不启用 Hot Reload。

## 十、故障隔离就是性能优化

异常重试、日志风暴、SystemUI 重启和 system_server 崩溃都会产生明显功耗和稳定性成本。

建议：

* 每个功能独立安装，单个功能失败不影响其他功能；
* 找不到 ROM 类、字段或方法时只记录一次；
* 失败后不要在高频路径重复探测；
* Release 日志必须限流；
* 不在每帧、每次触摸或每次通知刷新时输出日志；
* 对确定不兼容的功能使用“当前进程本次启动停用”机制；
* 不捕获异常后立即无限重试；
* 不用大范围 `try/catch` 掩盖真实根因；
* 不通过返回伪造结果让编译或测试表面通过。

对于关键进程，应优先保证安全降级：

* 功能失效可以接受；
* SystemUI、Launcher 或 system_server 崩溃不可接受；
* 安全降级必须可记录、可定位、不可重复刷屏。

## 十一、低抽象、强约束、热路径优先

“俄罗斯代码风格”不是严谨的软件工程分类，也不应对某个地区开发者进行统一概括。

本项目更合适的工程风格名称是：

> 低抽象、强约束、热路径优先的系统代码风格。

好的体现：

* 少依赖；
* 少线程；
* 少唤醒；
* 少重复状态；
* 边界清晰；
* 资源有唯一所有者；
* 故障可控；
* 兼容代码集中；
* 热路径直接且可预测；
* 每项优化都能解释减少了什么实际成本。

应避免：

* 超大类和超长方法继续膨胀；
* 魔法数字散布；
* 为减少一次调用而复制大量代码；
* 全局静态状态无生命周期；
* 绕过类型安全和生命周期安全；
* 删除兼容边界后依靠异常兜底；
* 为追求 Kotlin 形式而使用复杂 DSL、Flow 或集合链；
* 为所谓架构统一引入多层包装；
* 只有原作者能够理解或修改。

中间层不是越少越好。

应保留真正有价值的边界：

* 业务逻辑保持可读；
* Hook 适配层尽量薄；
* ROM 兼容层集中；
* API 101/102 差异集中；
* 公共资源只有明确所有者；
* 高频路径不承担兼容探测和对象构建。

---

## 十二、测量优先，而不是凭感觉优化

任何声称提升性能、降低内存或节省电量的修改，都应区分：

### 可以通过代码直接确认的结论

例如：

* 删除了一个永久轮询；
* 关闭功能后不再安装 Hook；
* 避免了每次回调复制参数数组；
* 消除了重复 Receiver 注册；
* 将反射查找移出高频路径；
* 缓存增加了容量限制。

### 必须通过测试才能确认的结论

例如：

* 电池续航提高多少；
* SystemUI CPU 占用下降多少；
* 页面帧率提高多少；
* 内存降低多少 MB；
* 唤醒次数减少多少。

未经同设备、同系统、同设置和同测试流程验证，不应在 Changelog 中写具体百分比收益。

推荐工具：

* Perfetto；
* Android Studio CPU/Memory Profiler；
* `dumpsys batterystats`；
* `dumpsys meminfo`；
* FrameMetrics/JankStats；
* LSPosed 和系统日志；
* Debug 构建中的回调次数、耗时和注册计数。

Debug 统计必须：

* Release 默认关闭；
* 不进入高频日志；
* 不改变正常执行时序；
* 不创建长期额外线程。

---

## 十三、优化停止条件

不应无限追逐微小优化。

以下情况应停止继续优化：

* 修改无法解释减少了什么实际成本；
* 收益只存在于低频冷路径；
* ART/R8 已经能够自动完成；
* 引入的复杂度超过潜在收益；
* 增加了兼容风险；
* 需要扩大 keep 规则才能维持；
* 没有可重复的测试证明；
* 修改影响了已经稳定的核心 Hook；
* 只是让代码行数更少或语法更“像 Kotlin”。

优先修复真实日志、实际卡顿、重复注册、长期任务和高频分配。

不要为了完成“全项目优化”而修改没有证据表明存在问题的代码。

---

## 十四、代码审查清单

每个功能至少记录：

* 所属进程；
* Hook 目标；
* 注册条件；
* 触发频率；
* 是否属于热路径；
* 使用的线程或 Handler；
* Receiver、Observer 和 Listener；
* 使用的静态状态；
* 缓存及容量；
* 是否持有 Context、View 或 ClassLoader；
* 功能关闭后的剩余成本；
* 设置变化是否需要重启；
* ROM/API 兼容路径；
* 失败后的降级行为；
* Release 混淆和资源压缩风险。

全项目重点审计：

1. 关闭后仍注册的 Hook；
2. 重复 Hook 和重复监听器；
3. 永久 Handler、Executor、Timer 和 Coroutine；
4. 无法注销的 Receiver 和 Observer；
5. 静态 Context、View 和 ClassLoader；
6. 无界 Map、List、Bitmap 和 Drawable 缓存；
7. 高频反射和资源名称查询；
8. 高频日志和异常重试；
9. UI 主线程上的磁盘、Binder 和 DexKit 操作；
10. Debug 正常但 R8 Release 失效的动态入口。

## 十五、版本与发布策略

版本策略不应基于某个地区开发者的假定风格，而应形成明确的项目发布规范。

原则：

* 不为每个内部修改发布版本；
* 一个版本对应一个完整、可解释的阶段目标；
* 修复必须经过构建、日志和实机验证；
* Changelog 记录用户可感知变化和阶段性工程成果；
* 不把每次重命名、格式化或内部小调整写入 Changelog；
* 测试 APK 与正式 Release 分离；
* 未完成实机验证时不创建正式 Release；
* Tag、commit、versionCode、versionName、APK 和 SHA-256 必须一致；
* 不为了版本号整齐合并未经验证的高风险改动。

建议当前路线：

### r14.9.0

* 完成 Java → Kotlin 重构；
* 保持 libxposed API 101 基线；
* 修复迁移回归和显性问题；
* 完成 API 101 环境实机验证；
* 建立稳定 Kotlin 基线。

### r14.10.0

* 使用 API 102 编译；
* 保持 `minApiVersion=101`；
* 实现 API 101 / API 102 单 APK 双兼容；
* 不启用 Hot Reload；
* 分别完成 API 101 和 API 102 实机验证。

### 后续独立阶段

* 建立完整的功能—进程—Hook—线程—监听器清单；
* 完成资源所有权治理；
* 增加 Debug 性能计数；
* 使用 Perfetto 和 Batterystats 对比；
* 根据测量结果决定是否保留优化；
* 只有生命周期治理完成后，再评估 API 102 Hot Reload。

---

## 最终判断标准

每项优化必须至少回答一个问题：

* 是否减少了 Hook 触发次数？
* 是否缩小了加载进程范围？
* 是否减少了线程调度或系统唤醒？
* 是否移除了轮询？
* 是否减少了高频对象分配？
* 是否将反射移出了热路径？
* 是否修复了重复注册或生命周期泄漏？
* 是否限制了长期缓存？
* 是否降低了异常重试和日志成本？
* 是否增强了 API、ROM 或 R8 兼容性？
* 是否有可重复的测试方法？

如果以上问题都无法回答，那么它大概率只是代码形式变化，而不是有价值的系统优化。
