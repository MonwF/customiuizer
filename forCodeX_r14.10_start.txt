## 五、工作阶段

### 阶段 A：冻结并验证 API 101 基线

任何 API 升级前，先执行：

1. 检查当前分支、HEAD、`git status` 和最近提交；
2. 搜索未完成的 `TODO()`、`NotImplementedError`、临时空实现、固定假返回值和被禁用功能；
3. 检查 Java/Kotlin 重复实现和动态引用风险；
4. 执行现有单元测试；
5. 执行 Debug 构建；
6. 执行当前 API 101 Release 构建；
7. 执行可用的 Lint、`lintRelease`、`lintVitalRelease`；
8. 记录基线 APK 文件名、大小、SHA-256、包名、版本号和签名证书摘要；
9. 保存基线构建结果，但不要提交 APK。

若 API 101 基线本身失败，先定位是否为环境问题或已有代码问题。不得在未知失败基础上继续升级 API 102。

### 阶段 B：官方 API 差异审查

只使用 libxposed 官方 API、service、example、Javadoc、源码和 Maven 元数据作为技术依据。

对比 API 101 与 API 102：

- `XposedModule` 和 `XposedModuleInterface` 生命周期；
- `XposedInterface`、`Chain`、`Hooker` 和 `HookHandle`；
- framework attach/detach 的内部变化；
- Remote Preferences 和 service；
- API 102 新增 Hot Reload、Hook replacement、detach；
- `targetApiVersion=102` 的行为限制；
- Legacy `de.robv.android.xposed` API 禁止条件；
- R8、类验证和二进制兼容风险。

不要根据旧博客、论坛转述或管理器名称推断接口行为。

### 阶段 C：实施最小双兼容改造

预期配置原则：

```properties
minApiVersion=101
targetApiVersion=102
staticScope=false
```

依赖原则上调整为 API/service 102 的官方稳定版本，例如：

```gradle
compileOnly "io.github.libxposed:api:102.0.0"
testImplementation "io.github.libxposed:api:102.0.0"
implementation "io.github.libxposed:service:102.0.0"
```

但实施前必须查询执行时的官方仓库和 Maven 元数据，确认 API 102 对应的稳定坐标。不要自动升级到 API 103 或其他更高接口，也不要顺带升级无关依赖。

双兼容要求：

- API 101 是最低运行基线；
- 原有核心 Hook 公共路径只依赖 API 101 已存在的能力；
- API 102 环境复用稳定公共路径；
- 只有确实需要 API 102 专属能力时才进行运行时判断；
- API 版本判断放在入口、初始化或其他冷路径；
- 不在每个高频 Hook 回调中重复判断 API；
- 不允许 API 102 专属类型、方法签名、父类、字段类型或静态初始化污染 API 101 必经加载路径；
- 不通过反射调用 libxposed API 来绕过版本限制；
- 不引入 Legacy `de.robv.android.xposed` API；
- 不通过降低 `targetApiVersion` 回避问题。

重点防止：

- `NoSuchMethodError`
- `NoClassDefFoundError`
- `AbstractMethodError`
- `IncompatibleClassChangeError`
- `VerifyError`
- `ClassNotFoundException`
- `HookFailedError`
- 设置应用进程意外解析 compileOnly libxposed 类型
- R8 将 Hooker 合并进普通 UI/启动类
- API 101 环境过早解析 API 102 类型

### 阶段 D：保守审查现有兼容层

重点审查但不要无理由推翻：

- `MainModule`；
- `HookerClassHelper`；
- `ModuleHelper`；
- `XposedHelpers`；
- `ResourceHooks`；
- Hook 注册和 unhook 路径；
- Remote Preferences；
- `META-INF/xposed/java_init.list`；
- `module.prop`；
- scope 配置；
- ProGuard/R8 规则。

必须保留：

- Hook target；
- Hook priority；
- 注册条件和顺序；
- before/after 顺序；
- 参数读取与修改；
- 提前返回和提前抛出；
- 原方法异常传播；
- after-hook 的结果/异常替换；
- 参数延迟实例化；
- ClassLoader 和进程边界；
- Java/Kotlin 静态互操作；
- Release 混淆后的 callback 识别。

`HookerClassHelper` 当前承担 API 101 旧行为适配，是高风险边界。只有发现 API 102 下存在明确不兼容或错误时才修改，不能为了“使用新 API”整体重写。

### 阶段 E：Kotlin 重构后二次审查

本阶段不是再次进行大规模 Java → Kotlin 迁移。

对当前重构结果进行第二轮审查，只修复有证据的问题：

- JVM 方法签名或 `@JvmStatic`/`@JvmField` 不正确；
- `object`/`companion object` 初始化时机变化；
- nullable/platform type 转换导致的运行风险；
- Java/Kotlin 属性访问器差异；
- Hook callback、异常语义或参数行为改变；
- R8 下动态入口、after callback 或反射入口失效；
- 重复 Hook、Receiver、Observer、Listener；
- 生命周期泄漏；
- 永久 Handler、Executor、Timer、Coroutine 或空轮询；
- 静态持有 Activity、Fragment、View、Context、ClassLoader；
- 无界缓存；
- 高频路径中的反射、偏好读取、Binder、磁盘、高频日志或明显临时分配；
- UI 生命周期和动画实现中的重复初始化或状态恢复错误。

保留有意义的 Java边界。不要仅为了提高 Kotlin 文件比例迁移 `MainModule`、`PreferenceFragmentBase` 或其他稳定 Java 文件。

每项“优化”必须说明实际减少了什么系统成本。无法说明收益、仅让代码更短、ART/R8 已可自动处理或会扩大兼容风险的修改，不要做。

### 阶段 F：分离提交

兼容改造与二次优化应尽量分成独立提交：

1. `build: prepare libxposed API 101/102 compatibility`
2. `compat: support libxposed API 101 and API 102`
3. `fix: post-Kotlin migration correctness fixes`
4. `perf: evidence-based lifecycle/hot-path optimizations`
5. `docs: update r14.10.0 testing status`

没有实际修改的类别不要制造空提交。

不要把无关格式化、Gradle Kotlin DSL、version catalog、dependencyGuard、AGP/Kotlin/AndroidX 全量升级或大型架构替换混入本阶段。

## 六、暂不启用 API 102 Hot Reload

本阶段仅实现 API 101 / API 102 正常冷启动和重启兼容。

不要启用：

```properties
autoHotReload=true
```

不要为了展示 API 102 新功能而主动实现：

- `onHotReloading`；
- `onHotReloaded`；
- Hook 原子替换；
- 自动 detach；
- 模块 ClassLoader 热卸载。

当前项目存在进程级静态状态、Remote Preferences、Hook、Receiver、Observer、Handler、协程、缓存和 DexKit/native 资源。Hot Reload 需要独立完成旧代 HookHandle、线程、回调、JNI 和 ClassLoader 的所有权治理，不属于本阶段。

## 七、性能与故障处理原则

固定优先级：

> 实际可运行 > 功能正确 > API 101 稳定 > API 102 兼容 > 系统稳定 > 性能与功耗 > 可维护性 > 形式简洁。

要求：

- 功能关闭时接近零额外成本；
- 未启用功能尽量不注册 Hook；
- 各进程只初始化真正需要的功能；
- 不增加轮询和空唤醒；
- 不增加永久后台任务；
- 不在热路径重复反射、版本判断、字符串格式化或集合分配；
- 不为双兼容引入大型抽象框架；
- 不通过吞异常、伪造返回值、禁用功能或扩大 keep 范围掩盖问题；
- 找不到 ROM 类/方法时只记录一次并安全禁用单项功能；
- 不允许异常重试或日志风暴；
- SystemUI、Launcher、system_server 的稳定性高于单项功能可用性。
